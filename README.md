# Mini NPU Simulator

MAC(Multiply-Accumulate) 연산으로 패턴이 십자가(Cross)인지 X인지 판별하는 Python 콘솔 앱입니다. 사용자가 직접 3×3 필터/패턴을 입력하거나, `data.json`에 저장된 5×5·13×13·25×25 데이터를 일괄 분석할 수 있습니다.

## 1. 실행 방법

### 환경

- Python 3.9.6 (`python3 --version`으로 확인)
- 외부 라이브러리 없음 — 표준 라이브러리 `json`, `time`만 사용

### 실행 명령어

```bash
python3 main.py
```

실행하면 모드를 선택합니다.

```
[모드 선택]
1. 사용자 입력 (3x3)
2. data.json 분석
선택:
```

- **모드 1**: 필터 A, 필터 B, 패턴을 각각 3줄씩 공백으로 구분해 직접 입력합니다. 입력한 패턴이 필터 A/B 중 어느 쪽에 더 가까운지 MAC 점수로 판정합니다.
- **모드 2**: 같은 폴더의 `data.json`을 읽어 크기별(5/13/25) 필터를 불러오고, 저장된 패턴 케이스들을 일괄 채점한 뒤 성능 표와 결과 요약을 출력합니다.

## 2. 구현 요약

### 라벨 정규화

`data.json`은 같은 의미의 라벨을 세 갈래로 다르게 표기합니다.

- `filters` 안의 키: `"cross"`, `"x"` (소문자)
- `patterns`의 `expected` 값: `"+"`, `"x"`
- 프로그램이 내부적으로 쓰고 화면에 출력하는 표준 라벨: `'Cross'`, `'X'`

```python
LABEL_MAP = {
    '+': 'Cross',
    'cross': 'Cross',
    'Cross': 'Cross',
    'x': 'X',
    'X': 'X',
}
```

[main.py:17-23](main.py#L17-L23)의 `normalize_label(raw)`는 `raw`가 표에 있으면 표준 라벨을, 없으면 `None`을 반환합니다. `load_filters`([main.py:229](main.py#L229))는 필터 이름을 정규화해서 못 찾으면 경고 후 건너뛰고, `analyze_patterns`([main.py:264](main.py#L264))는 `expected` 값을 정규화해서 `None`이면 해당 케이스를 즉시 FAIL 처리합니다(`'expected 라벨 오류'`). 즉 "표에 없는 표기 = 판정 불가능한 데이터"로 취급해 프로그램이 죽지 않고 케이스 단위로만 실패하도록 설계되어 있습니다.

### MAC 연산

[main.py:25-31](main.py#L25-L31)의 `mac(pattern, filter_grid)`는 이중 `for`문으로 두 격자의 원소별 곱을 모두 더합니다.

```python
def mac(pattern, filter_grid):
    total = 0
    size = len(pattern)
    for i in range(size):
        for j in range(size):
            total = total + pattern[i][j] * filter_grid[i][j]
    return total
```

크기를 3으로 고정하지 않고 `size = len(pattern)`으로 입력 자체에서 크기를 뽑아 쓰기 때문에, 3×3(모드 1)부터 5×5·13×13·25×25(모드 2, `data.json`)까지 같은 함수 하나로 처리됩니다. 실제로 `performance_section`([main.py:157](main.py#L157))에서 3/5/13/25 네 가지 크기를 모두 이 `mac()` 하나로 측정합니다.

### 동점 처리 (epsilon)

부동소수점 연산은 수학적으로 같은 값이라도 계산 경로에 따라 미세하게 다른 비트 표현을 가질 수 있습니다(예: `0.9`와 `0.8999999999999999`). 이 오차를 그대로 `>` 비교하면 실제로는 동점인 두 점수 중 하나가 "근거 없이" 이겨버립니다.

그래서 [main.py:81-90](main.py#L81-L90)의 `judge()`는 크기 비교보다 **먼저** 오차 허용 검사를 합니다.

```python
def judge(score_a, score_b, label_a, label_b):
    if abs(score_a - score_b) < EPSILON:
        return 'UNDECIDED'
    if score_a > score_b:
        return label_a
    return label_b
```

`EPSILON = 1e-9`([main.py:4](main.py#L4))입니다. 이 순서가 바뀌어 크기 비교(`>`)가 먼저 오면, `abs(a-b) < EPSILON`인 사실상 동점 상황도 부동소수점 오차 방향에 따라 무조건 한쪽이 승자로 결정되어버려 동점 검사 자체가 무의미해집니다. `judge()`는 모드 1(`'A'`/`'B'`)과 모드 2(`'Cross'`/`'X'`)에서 라벨만 바꿔 그대로 재사용됩니다.

### 실패 원인 분석

실패 3건을 세 가지 가능성으로 순서대로 점검했습니다.

**① 데이터/스키마 문제인가** — 아닙니다. `data.json`의 `filters`/`patterns` 키 구조는 `size_5`/`size_13`/`size_25` 세 크기 모두 정상적으로 로드됐고(`OK size_5 필터 로드 완료 (Cross, X)` 등), 6개 패턴 케이스 모두 크기 추출·필터 매칭·패턴 크기 검증·`expected` 라벨 정규화 4단계를 전부 통과해 채점 단계까지 도달했습니다. 관문 실패로 인한 FAIL은 0건입니다.

**② 로직 문제(MAC 계산이나 `judge` 자체가 틀림)인가** — 아닙니다. 통과한 3개 케이스를 보면 Cross 점수와 X 점수의 차이가 매우 뚜렷합니다.

| 케이스 | Cross 점수 | X 점수 | 차이 |
|---|---|---|---|
| size_5_2 | 8.9 | 0.1 | 8.8 |
| size_13_1 | 0.3 | 14.700000000000008 | 14.4 |
| size_25_2 | 52.9 | 0.1 | 52.8 |

차이가 소수점 이하가 아니라 정수 단위로 크기 때문에, `mac()`이나 `judge()`의 계산 로직 자체가 틀렸다면 이렇게 큰 차이로 정답과 일치하는 결과가 나올 수 없습니다. 즉 로직은 정상 동작하고 있습니다.

**③ 수치 비교(부동소수점) 문제인가** — 그렇습니다. 실패한 3개 케이스의 Cross/X 점수 차이를 직접 계산하면:

| 케이스 | Cross 점수 | X 점수 | `abs(차이)` |
|---|---|---|---|
| size_5_1 | 0.9 | 0.8999999999999999 | 1.11 × 10⁻¹⁶ |
| size_13_2 | 7.499999999999997 | 7.5 | 2.66 × 10⁻¹⁵ |
| size_25_1 | 4.9 | 4.899999999999999 | 1.78 × 10⁻¹⁵ |

세 경우 모두 `EPSILON = 1e-9`보다 훨씬 작습니다. 두 점수는 사람이 보기엔 소수점 15~16번째 자리에서만 다르고, 수학적으로는 완전히 같은 값(대칭 패턴 × 대칭 필터 조합이 만들어내는 항등한 합)입니다. 부동소수점 덧셈 순서에 따라 표현 오차가 미세하게 갈렸을 뿐, 원래 값은 동점입니다.

**결론**: 이 3개 케이스는 Cross와 X 중 어느 쪽이 "더 크다"고 원리적으로 판별할 수 없는 입력입니다. `judge()`가 `EPSILON` 기준으로 `UNDECIDED`를 반환한 것은 오답이 아니라, 판별 불가능한 상황을 정직하게 보고한 정상 동작입니다.

### 시간 복잡도 분석

실제 성능 표(모드 2, `REPEAT=10`회 평균):

| 크기 | 평균 시간(ms) | 연산 횟수(N²) |
|---|---|---|
| 3×3 | 0.0022 | 9 |
| 5×5 | 0.0044 | 25 |
| 13×13 | 0.0236 | 169 |
| 25×25 | 0.0824 | 625 |

`mac()`은 이중 `for`문으로 한 변의 길이가 N이면 곱셈·덧셈이 정확히 N² 번 일어납니다. 구간별로 "한 변 배수"와 "연산 횟수 배수"를 비교하면:

| 구간 | 한 변 배수 | 연산 횟수 배수 (= 한 변 배수²) | 실측 시간 배수 |
|---|---|---|---|
| 3→5 | ×1.667 | ×2.778 | ×2.000 |
| 5→13 | ×2.600 | ×6.760 | ×5.364 |
| 13→25 | ×1.923 | ×3.698 | ×3.492 |
| 3→25 (전체) | ×8.333 | ×69.444 | ×37.455 |

연산 횟수 배수가 정확히 한 변 배수의 **제곱**으로 나타나며(예: 5→13 구간 한 변 ×2.6 → 연산 횟수 ×6.76 = 2.6²), 이는 `mac()`이 O(N²)임을 그대로 보여줍니다.

다만 실측 시간 배수는 모든 구간에서 이론값(연산 횟수 배수)보다 작습니다(예: 3→25 구간 이론상 ×69.4배가 되어야 하지만 실측은 ×37.5배). 이는 작은 크기일수록 함수 호출, 리스트 인덱싱, `range()` 객체 생성 등 N²에 비례하지 않는 **고정 비용**의 비중이 상대적으로 커서, 크기가 커질 때 실제 순수 연산 시간의 증가폭이 곱셈·덧셈 횟수의 증가폭만큼 온전히 드러나지 않기 때문입니다(3×3처럼 연산 자체가 9번뿐인 경우 총 시간의 대부분이 고정 오버헤드). 크기가 커질수록(5→13, 13→25) 실측 배수가 이론 배수에 점점 가까워지는 경향도 이 설명과 일치합니다.

### FAIL 3개에 대한 결론

`size_5_1`, `size_13_2`, `size_25_1` 3건의 FAIL은 `mac()` 계산이나 `judge()` 판정 로직의 결함이 아닙니다. 통과한 3개 케이스가 보여주듯 로직 자체는 정상이며, 실패한 3개는 Cross 점수와 X 점수가 부동소수점 표현상 15~16번째 소수 자리에서만 다를 뿐 수학적으로 완전히 동일한 값을 갖는, **원리적으로 판별이 불가능한 입력 데이터**입니다. `EPSILON` 기반 동점 처리가 이를 `UNDECIDED`로 정직하게 보고했고, 그 결과가 `expected`와 다르므로 FAIL로 집계된 것뿐입니다. 즉 이 3건은 구현 결함이 아니라 데이터 특성에 의한 정상 동작입니다.

## 보너스 과제 1 — 1차원 배열 최적화

### 구현

`main.py`에는 2차원 MAC 연산을 1차원으로 최적화하는 두 함수가 추가되어 있습니다.

- [flatten(grid)](main.py#L38-L45): 2차원 격자를 1차원 리스트로 폅니다. 행을 위에서부터 순서대로 이어붙이므로(`[[1,2],[3,4]]` → `[1,2,3,4]`) 결과 길이는 항상 `N*N`이고, 원소가 등장하는 순서(따라서 덧셈 순서)는 원본 2차원 순회와 완전히 동일합니다.
- [mac_flat(flat_a, flat_b)](main.py#L47-L53): 1차원 리스트 두 개를 받아 MAC 연산을 수행합니다. 두 리스트가 `flatten()` 결과처럼 길이가 같다고 전제하고, 인덱스 `k` 하나로 순회합니다.

`mac()`과 `mac_flat()`의 차이는 반복문 구조와 인덱싱 방식뿐이고, 곱셈이 일어나는 횟수 자체는 바뀌지 않습니다.

| 항목 | `mac()` (2D) | `mac_flat()` (1D) |
|---|---|---|
| 반복문 구조 | 이중 `for` (`i`, `j`) | 단일 `for` (`k`) |
| 원소 접근 | `pattern[i][j]`, `filter_grid[i][j]` (인덱싱 2회) | `flat_a[k]`, `flat_b[k]` (인덱싱 1회) |
| 곱셈 횟수 | N² | N² (동일) |
| 시간복잡도 | O(N²) | O(N²) (동일) |

즉 이 최적화는 알고리즘의 점근 복잡도를 바꾸는 게 아니라, 반복문을 2겹에서 1겹으로 줄이고 인덱싱 횟수를 절반으로 줄여서 **O(N²)의 상수 계수만 줄이는** 최적화입니다.

### 측정 조건

`compare_section()`([main.py#L214-L246](main.py#L214-L246))에서 2D(`mac()`)와 1D(`mac_flat()`)를 동일 입력·동일 반복 횟수로 비교합니다.

- 입력: `data.json`의 Cross 필터(5×5, 13×13, 25×25), 3×3은 `data.json`에 없으므로 `make_cross(3)`으로 생성
- 반복 횟수: 2D·1D 모두 `BONUS_REPEAT = 1000`([main.py#L6](main.py#L6))회 평균. 기본 과제 성능표에 쓰는 `REPEAT = 10`([main.py#L5](main.py#L5))과는 별도 상수

`BONUS_REPEAT`를 1000으로 늘린 이유는, 오늘 비교하는 대상이 "크기별 차이"가 아니라 "같은 크기 안에서 2D와 1D의 차이"이기 때문입니다. 이 차이는 크기별 차이보다 훨씬 작아서, `REPEAT = 10`처럼 적은 횟수로 측정하면 측정 잡음(시스템 스케줄링, GC 등)이 실제 차이보다 커져 개선율의 부호 자체가 뒤집히는 현상이 발생합니다. 반복 횟수를 1000회로 늘려 평균을 안정시켜야 2D가 1D보다 느리다는 실제 경향이 잡음에 묻히지 않고 드러납니다.

### 측정 결과

`python3 main.py` 실행 후 모드 3(최적화 비교)을 선택했을 때의 실제 콘솔 출력입니다.

```
#---------------------------------------
# 최적화 비교 (2D vs 1D, 평균/1000회)
#---------------------------------------
크기       2D(ms)      1D(ms)     개선율   결과일치
----------------------------------------------------
3x3          0.00213     0.00102      52.3%       OK
5x5          0.00430     0.00221      48.7%       OK
13x13        0.02340     0.01332      43.1%       OK
25x25        0.08180     0.05138      37.2%       OK
```

네 크기 모두 결과일치가 `OK`입니다. `flatten()`이 행 순서를 그대로 이어붙여 덧셈 순서를 보존하므로, `mac()`(2D)과 `mac_flat()`(1D)의 계산 결과는 부동소수점 표현까지 비트 단위로 같아야 정상이고, `compare_section()`은 이를 `==` 비교로 직접 검증합니다(`score_2d == score_1d`, [main.py#L237](main.py#L237)).

### 해석 1 — 개선율이 크기별로 다른 이유

개선율은 크기가 커질수록 52.3% → 48.7% → 43.1% → 37.2%로 꾸준히 줄어듭니다. `mac()`이 `mac_flat()`보다 더 드는 비용은 크게 두 갈래로 나뉩니다.

- 안쪽 `range(size)` 재생성 비용: 바깥 `for i` 루프가 돌 때마다 안쪽 `range(size)`를 새로 만드는 비용으로, 바깥 루프 횟수(N)에 비례
- 원소 접근(인덱싱) 비용: `[i][j]` 2회 접근 vs `[k]` 1회 접근의 차이로, 전체 원소 수(N²)에 비례

`range()` 셋업 비용은 N에 비례하고 전체 연산량은 N²에 비례하므로, 크기가 커질수록 `range()` 셋업 비용이 전체 시간에서 차지하는 비중은 상대적으로 줄어듭니다. 반대로 인덱싱 비용(N²에 비례)의 비중은 유지됩니다. 즉 작은 크기일수록 "N에 비례해서 줄어드는 고정비성 비용"의 상대적 영향이 커서 개선율이 크게 나타나고, 크기가 커질수록 그 비중이 희석되면서 개선율이 점점 작아지는 것입니다.

### 해석 2 — flatten 비용을 포함하면 결과가 뒤집힐 수 있음

지금까지의 비교는 `flatten()` 변환 자체의 비용을 측정 구간 밖에 두고(`compare_section()`에서 `flat = flatten(grid)`을 시간 측정 이전에 미리 해둠, [main.py#L230](main.py#L230)) 순수 MAC 연산 시간만 비교한 것입니다. 하지만 실제로 "매번 새 입력을 변환해서 쓰는" 상황이라면 `flatten()` 비용도 매번 지불해야 합니다. 25×25 기준으로 이를 직접 측정하면:

```
flatten() 1회 평균 시간 (25x25): 0.03112 ms
mac_flat() 1회 평균 시간 (25x25): 0.05040 ms
flatten() + mac_flat() 합계:      0.08152 ms
mac() (2D) 1회 평균 시간:          0.08180 ms
```

`flatten()` + `mac_flat()`의 합계(0.08152ms)는 `mac()`(2D, 0.08180ms)와 거의 같습니다. 즉 위 측정 결과 표에서 25×25가 보여준 37.2%라는 개선율은 "이미 펴진 1차원 배열을 재사용할 때"만 유효한 수치이고, 매번 `flatten()`부터 다시 해야 한다면 그 개선폭은 거의 전부 사라져 사실상 2D와 동등한 수준(오히려 변환 오버헤드 자체의 변동에 따라 더 느려질 수도 있는 수준)이 됩니다.

**결론**: 이 최적화는 "한 번 변환해서 여러 번 재사용하는 경우"에만 유효합니다. 이 미션의 구조(필터를 `load_filters()`로 한 번 로드한 뒤 여러 패턴에 반복 적용)에서는 필터를 한 번만 `flatten()`하고 여러 패턴과 비교하는 방식으로 쓰면 변환 비용을 분산시킬 수 있어 이득이 남습니다. 하지만 입력이 매번 바뀌어서 매 호출마다 새로 변환해야 하는 구조라면, 변환 비용이 MAC 연산 자체의 절감분을 상쇄해 최적화의 실질적 이득이 없어집니다.

## 보너스 과제 2 — 패턴 생성기

`main.py`에는 [make_cross(size)](main.py#L126-L140), [make_x(size)](main.py#L143-L155) 함수가 구현되어 있습니다.

- `make_cross(size)`: 가운데 행(`i == mid`)과 가운데 열(`j == mid`)을 1.0, 나머지를 0.0으로 채운 `size × size` 십자가 패턴을 생성합니다.
- `make_x(size)`: 왼쪽 위→오른쪽 아래 대각선(`i == j`)과 오른쪽 위→왼쪽 아래 대각선(`i + j == size - 1`)을 1.0, 나머지를 0.0으로 채운 `size × size` X 패턴을 생성합니다.

`data.json`에는 3×3 크기의 필터가 없기 때문에, `performance_section()`([main.py:157-173](main.py#L157-L173))에서 3×3 성능 측정용 데이터가 필요할 때 `make_cross(3)`으로 직접 생성해서 사용합니다(위 성능 표의 `3x3` 행). 5/13/25는 `data.json`에서 로드된 필터를 그대로 재사용합니다.
